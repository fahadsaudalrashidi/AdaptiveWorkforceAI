# Arabic Letter Fix, Design Consistency, and Arabic Proofreading — 4 Newest Pages

Three priorities, in the order requested: (1) the HR Letter Generator's reported Arabic
bug, (2) a design-consistency pass on GOSI/Payroll Budget/HR Letters/Zakat against the
Phase 15 system, (3) Arabic proofreading of the same four modules' UI text.

## Priority 1 — Root cause and fix

### What investigation actually found

The bug report described "selecting Arabic still produces an English letter." Before
touching code, this was investigated end-to-end rather than assumed:

1. **Engine unit test** — called `build_salary_certificate(employee, company, language="ar")`
   directly. Result: a fully correct, fully Arabic document (Arabic salutation, Arabic
   body sentences, Arabic signature block).
2. **Route-level test (TestClient)** — POSTed to `/hr-letters/generate-single` with
   `language=ar`. Same correct Arabic result.
3. **Browser-level network interception** — launched the real app, filled the form,
   clicked the "العربية" toggle, and intercepted the actual multipart POST body sent to
   the backend. The `language` field in the real request was `ar` — confirmed both by
   reading the raw request buffer and by checking the toggle button's own CSS state
   (visibly selected/highlighted).

**Conclusion: the language branch selection itself — frontend state, the POST field, and
the backend's `if language == "ar"` dispatch — was never broken.** No code path was found
anywhere that silently forces `language="en"`.

**What WAS reproduced and is a real, confirmed defect**: a Word bidi-rendering artifact
whenever a value in one script is interpolated inline into a sentence written in the
other script. Generating an **English** Salary Certificate with an **Arabic** company
name (`شركة الأفق للحلول التقنية`) reproduced the exact symptom from the bug report:

```
This is to certify that Sara Al-Otaibi (Employee ID: HLEMP001) is currently employed
with شركة الأفق للحلول التقنية as Senior Analyst in the Finance department, since
01 March 2018.
```

Word's bidi algorithm resolves each embedded run's edges independently; an unisolated
Arabic run inside an LTR paragraph (or vice versa) renders with the exact "irregular
spacing" the report described. This most plausibly explains what was actually observed —
a company name/signatory typed in one script while generating in the other language (an
easy, natural thing to do while testing) produces visually broken output that reads as
"the language didn't apply," even though the template itself was correct.

### The fix (two parts, `backend/core/hr_letter_generator.py`)

1. **Department translation** — `_translate_department_for_letter()`
   ([line ~230](backend/core/hr_letter_generator.py)) reuses
   `department_normalizer.py`'s `EN_AR_DEPARTMENT_SYNONYMS` table directly (real reuse,
   not a new list) to render common department names in Arabic
   (`"Finance"` → `"مالية"`, `"Human Resources"` → `"الموارد البشرية"`). Falls back to the
   original value, never fabricated, for any department not in that curated table.
2. **Bidi isolation for everything else** — job titles are open free text this platform
   cannot reliably translate (unlike the small, bounded department vocabulary), so
   instead of translating them, `_bidi_isolate()` wraps any inline-interpolated value
   (name, employee ID, job title, hire date, wage column name, and the company
   name/signatory wherever they appear mid-sentence) in Unicode directional-isolate marks
   (U+2066/U+2067 … U+2069) whenever its script doesn't match the surrounding paragraph's
   language. This is the same technique `LatinText.tsx`
   (`executive-ui/src/components/shared/LatinText.tsx`, `dir="ltr"` +
   `unicode-bidi: isolate`) already established for this platform's RTL tables — applied
   here at the text level since Word paragraphs don't have a CSS equivalent, and applied
   symmetrically (LTR-in-RTL and RTL-in-LTR) since a user can type either script into the
   company-details form regardless of the document language selected.

## Priority 2 — Design consistency pass

Reviewed all 4 pages (GOSI Calculator, Payroll Budget Planner, HR Letter Generator, Zakat
Estimator) against the Phase 15 system (`StatusBadge`/`StatusBanner`/`StatusLegend`,
`design-tokens.ts`'s 5-tone system, `LatinText.tsx`). Findings and fixes, per page:

**GOSI Calculator**
- Missing `<StatusLegend />` (present on all 11 other data-bearing pages, absent here) —
  added, placed identically (after the header, before the first banner).
- **Double-icon bug**: the top disclaimer banner manually embedded an `AlertTriangle`
  icon inside `StatusBanner tone="critical"`'s children, while `StatusBanner` itself
  already renders a default icon (`ShieldAlert`) in that tone — the banner was rendering
  TWO icons side by side. Fixed by passing `icon={AlertTriangle}` as a prop instead of
  duplicating it in children (matches the component's intended API — this exact
  duplication pattern, copied from Phase 21's Labor Law Calculators page, had silently
  existed there too, though that page was outside this pass's explicit scope).
  Confirmed via before/after screenshot: was two overlapping icons, now one.
- Sources list used a `ShieldCheck` icon per bullet — inconsistent with the established
  plain-bullet convention used identically by both Labor Law Calculators and this
  session's own Zakat page (`· {source}`). Reverted to match.
- `record_id_safe` table cells wrapped in `<LatinText>` — the established Phase 15
  component for Latin-script IDs inside RTL tables (previously only used on
  EmployeeRiskDashboard/SuccessionReadinessTracker; this page had no isolation at all).

**Payroll Budget Planner**
- Missing `<StatusLegend />` — added.
- No double-icon issue found (this page never manually embedded a duplicate icon).
- Inline manual-entry table inputs already used the platform's standard input styling
  (`rounded-lg`/`rounded-md`, `border-slate-200`, `bg-white dark:bg-slate-800`,
  `focus:border-blue-400`) — reviewed against `EmployeeRiskDashboard.tsx`'s established
  input pattern and confirmed consistent; no change needed.

**HR Letter Generator**
- Missing `<StatusLegend />` — added.
- Same double-icon bug as GOSI (manually-embedded `AlertTriangle` duplicating the
  critical banner's default icon) — fixed identically.
- Employee ID table cells wrapped in `<LatinText>`.
- **New**: a light, non-blocking inline warning when a company-details field is
  suspiciously short (1–2 characters after trimming) — e.g. typing "AB" as the company
  name now shows *"The following fields look unusually short: Company name — this flows
  directly into an official-looking document, so double-check it's not placeholder text
  before generating."* This is a UX safety net only (per the brief's explicit framing),
  never blocks generation, and makes no claim about truthfulness beyond length.
  Live-verified: entering "AB" as company name triggered the warning; "CHRO" (4 chars) as
  signatory title correctly did not.

**Zakat Estimator**
- Missing `<StatusLegend />` — added.
- **Two** double-icon instances found and fixed: the top methodology-gap banner
  (`ShieldAlert` manually embedded, duplicating `StatusBanner`'s own default critical
  icon — same icon twice, harder to notice than GOSI's mismatched-icon case but the same
  underlying bug) and the "missing required field" banner (`AlertTriangle` manually
  embedded, duplicating `caution`'s own default `AlertTriangle`).
- The 4-field manual-entry form already used the same input styling convention as the
  other 3 pages — reviewed, consistent, no change needed.

**Not changed / reviewed and found not applicable**: the canonical `ProgressRing` (via
`KPICard`'s `radialPct`) is used elsewhere only for genuinely bounded 0–100% metrics
(e.g. WPS mismatch rate). None of the 4 pages have a natural bounded-percentage KPI —
Payroll Budget's variance can exceed 100% or go negative, GOSI has no single rate metric
comparable to WPS's — so none was force-fitted in, matching the restraint the Gratuity/
Leave tabs on the Labor Law page already show (they don't use `radialPct` either).

All 4 pages were screenshotted after fixes in both English and Arabic (via the
platform-wide language toggle, not the HR Letter Generator's separate document-language
selector) with zero browser console errors across the full verification session. RTL
mirroring (sidebar, table column order, StatusLegend Arabic labels) rendered correctly
on every page.

## Priority 3 — Arabic language corrections

Reviewed every Arabic string in `labor_law_calculators.py`, `SaudiLaborLawCalculators.tsx`,
`gosi_calculator_engine.py`, `GosiCalculator.tsx`, `payroll_budget_engine.py`,
`PayrollBudgetPlanner.tsx`, `zakat_estimator_engine.py`, `ZakatEstimator.tsx`, and (for

Generator's own page chrome is distinct from Priority 1's letter *templates*)
`hr_letter_generator.py`'s non-template disclaimer/narrative strings and
`HRLetterGenerator.tsx`'s page UI. Five corrections found and applied:
