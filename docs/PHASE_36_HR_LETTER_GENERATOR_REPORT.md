# Phase 36 — Automated HR Letter Generator

A new module producing real, named official employee Word documents from uploaded
workforce data (`backend/core/hr_letter_generator.py`) — a mail-merge feature common on
established Saudi HR platforms. This module is a deliberate exception to every prior
module's PII-avoidance discipline: its entire purpose is to produce real correspondence
carrying real employee names, so `record_id_safe`-style anonymization would defeat the
point. The safety discipline shifts instead to scope restriction, zero fabrication, and a
mandatory draft/review marking on every document — detailed below.

## 1. Letter types built, and why the two disciplinary ones were excluded

**Built (3 types):**

| Letter type | Requires |
|---|---|
| Salary Certificate (خطاب تعريف بالراتب) | Name, ID, job title, department, hire date, **clean numeric** salary |
| Employment Certificate (خطاب تعريف بالعمل) | Name, ID, job title, department, hire date |
| End-of-Service Settlement (تسوية نهاية الخدمة) | The above + a REAL computed gratuity figure, cross-linked from Phase 21's calculator |

**Explicitly NOT built — Warning/disciplinary letters (خطاب إنذار) and termination
letters.** Both require a case-specific human judgment call about employee conduct or
separation circumstances that this platform has no reliable data to support. A Salary or
Employment Certificate only *restates facts already present in the uploaded row*
(position, department, tenure, pay); a warning or termination letter would require the
platform to assert something about an employee's conduct it cannot actually know, with
real legal exposure for the issuing company and the named employee if generated from a
template without genuine case-specific review. This reasoning is documented in the
module's docstring
([`hr_letter_generator.py:12-23`](backend/core/hr_letter_generator.py#L12-L23)) and
surfaced to the user directly on the page (`EXCLUDED_LETTER_TYPES_NOTE_EN/AR`,
[lines 126-136](backend/core/hr_letter_generator.py#L126-L136)) — not just noted here.
`LETTER_TYPES` ([line 122](backend/core/hr_letter_generator.py#L122)) is a closed
3-element tuple; there is no code path that adds a 4th type.

## 2. Every other safety discipline carried over from this session

- **Never fabricates.** The Salary Certificate reuses the exact strict numeric-salary
  rule Phase 21's `labor_law_calculators.py` established for Article 84/111 legal
  figures — `_extract_strict_numeric()`
  ([`hr_letter_generator.py:195-206`](backend/core/hr_letter_generator.py#L195-L206)) is
  a small local reimplementation (not a cross-import of that module's private
  underscore-prefixed helper — same per-module duplication convention
  `job_pattern_grouping_engine.py`/`contract_expiry_engine.py` document). If a salary
  value is range-text or otherwise not a clean number, `build_salary_certificate()`
  returns `available=False` with a reason and **generates no document at all** rather
  than approximating a legally-relevant figure written into an official bank/visa-facing
  certificate — verified in `test_range_text_salary_refuses_not_approximates` and live
  below (Khalid, HLEMP004).
- **Draft/review marking on every document.** `_add_draft_marking()`
  ([line 456](backend/core/hr_letter_generator.py#L456)) renders
  `DRAFT — REQUIRES HUMAN REVIEW & AUTHORIZED SIGNATURE BEFORE OFFICIAL USE` in bold red,
  center-aligned, near the bottom of every letter of every type, in every language —
  enforced structurally (called once from `_finalize_document()`, the single exit path
  every `build_*` function routes through) rather than duplicated per letter type.
- **Footer disclosure.** `_add_footer_note()`
  ([line 466](backend/core/hr_letter_generator.py#L466)) states the document was
  generated by the platform from uploaded data on a given date, and is not an original
  signed HR record — same structural guarantee.
- **Company identity is never assumed.** `CompanyDetails` (company name, address,
  signatory name/title) is a required, explicit user input at generation time, not
  inferred from the dataset — the frontend form disables both generate buttons until all
  four fields are filled.

## 3. End-of-Service cross-link — implementation and verification

Per the route-layer-decoupling precedent Phase 8 (succession) and Phase 18 (contract
expiry) established: `hr_letter_generator.py` does **not** import
`labor_law_calculators.py`, and that module does not import this one
([module docstring, lines 46-63](backend/core/hr_letter_generator.py#L46-L63)).
`build_end_of_service_letter()` never computes a gratuity figure — it only accepts one as
a parameter (`gratuity_amount_sar`, `gratuity_scenario`, `years_of_service`,
`monthly_wage_sar`, `wage_column_name`, `gratuity_computed_at`) and formats it into a
letter, so the real Article 84/85 math lives in exactly one place.

The join key is `record_id_safe`
(`sha256(raw_id)[:6].upper()`, `"EMP-"`-prefixed) — the same hash
`labor_law_calculators._safe_record_id()` produces. `safe_record_id_for_lookup()`
([`hr_letter_generator.py:186-194`](backend/core/hr_letter_generator.py#L186-L194)) is a
small **public** reproduction of that hash function (explicitly not the gratuity math)
so the route layer can compute the same key for a raw employee ID and match it against a
`GratuityCandidate`. The route layer
(`local_analysis_routes.py`'s `/hr-letters/employees`, `/hr-letters/generate-single`, and
`/hr-letters/generate-bulk`) is the only place that runs both `analyze_gratuity()` and
`extract_employee_letter_records()` on the same upload and joins them.

**Verified exact-match, not just "a number was produced":**
`test_gratuity_figure_matches_labor_law_calculator_exactly` calls
`analyze_gratuity()` directly on the fixture, calls `build_end_of_service_letter()` with
that exact candidate's `applicable_amount_sar`, and asserts the formatted SAR string
appears verbatim in the generated document text — for Reem Al-Subaie (HLEMP010: 12 years,
SAR 20,000/month, resignation → 10+ year tier = full award = **SAR 190,000.00**, hand-
verified: `20000×5×0.5 + 20000×7×1.0 = 50,000 + 140,000 = 190,000`). Live-verified
identically via the real running backend (§5).
`test_declining_scenario_when_gratuity_not_computable` confirms Khalid (range-text
salary) never appears in the gratuity candidate set, and the bulk generator correctly
skips him for this letter type with a stated reason rather than a fabricated figure.
