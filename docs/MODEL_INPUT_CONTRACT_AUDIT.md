## 1. Purpose and Scope

### 1.1 What Is the Model Input Contract?

`ModelInputContract` (`backend/core/model_input_contract.py`, introduced in Phase 4) is a pre-training validation gate that inspects the list of feature names proposed for ML training or inference before any model code runs. It enforces a set of scientific and governance rules intended to prevent four categories of harm:

1. **Target leakage:** The outcome variable or a proxy of it appears as a feature, making the model appear to predict what it actually already knows.
2. **Legacy scientific harm:** A construct computed from an invalid formula (Layer B/C of `feature_factory.py`) enters the model, producing feature importances and SHAP values that are mathematically meaningless.
3. **Identity memorization:** Row-level identifier columns allow the model to memorize individual employees rather than learning generalizable patterns.
4. **Preprocessing leakage:** Columns whose names suggest whole-dataset transformation (scaling, imputation, encoding) may carry test-set statistics into training, inflating evaluation metrics.

The contract acts as a strict gatekeeper: if any CRITICAL or HIGH violation is found, the feature set is declared invalid (`is_valid = False`) and the pipeline must not proceed to model training or inference.

### 1.2 Scope

The contract governs:

- All feature sets passed to `MLRouter` during training
- All feature sets used during inference (prediction calls)
- Any feature set generated by `FeatureFactory.engineer()` or `TheoryGroundedConstructEngine.compute()` before it reaches the model layer

The contract does **not**:

- Modify the DataFrame
- Remove columns from the feature set (blocking is advisory; the caller must act on it)
- Train, evaluate, or score any model
- Override governance decisions made by `TheoryAwareColumnMapper` (Phase 1)
- Substitute valid features for blocked ones

### 1.3 Design Philosophy

The contract is deliberately conservative. It is a name-based heuristic scanner, not a semantic content analyzer. It will produce false positives (clean columns flagged due to keyword overlap) and may miss false negatives (harmful columns whose names do not trigger any keyword). Section 11 documents these known limitations explicitly.

The intent is to catch gross violations automatically and force manual review of edge cases. It is not a substitute for the human science review process.

## 2. Architecture Position

```
Upload / Data Ingest
        |
        v
DatasetProfiler + DataHealer
        |
        v
TheoryAwareColumnMapper  (Phase 1 — column mapping + leakage_flag)
        |
        v
TheoryGroundedConstructEngine  (Phase 2 — theory constructs computed)
        |
        v
FeatureFactory.engineer()  (Layer A, D, E — interaction + temporal features)
        |
        v
>>> ModelInputContract.validate()  <-- THIS COMPONENT
        |
        v (only if is_valid == True)
MLRouter → model training / inference
```

The contract is the last validation step before the model layer. It has access to:
- The complete list of feature names as they will be passed to the model
- The Phase 1 `column_mappings` dict (which carries `leakage_flag` and `evidence_strength` per column)
- The target column name
- Optionally, the full DataFrame (for future cardinality checks — not currently used by any check)

## 3. Check Order Reference Table

Checks are evaluated in the order shown below. Within a single feature, evaluation stops at the first violation that triggers a `continue` (all checks except `PREPROCESSING_LEAKAGE`). This means a feature cannot accumulate multiple violation types from a single pass; the first match wins.

| Check # | Violation Type | Severity | Blocks Feature? | Trigger Condition |
|---|---|---|---|---|
| 0 | (Pre-approval — no violation) | None | No — skips all checks | Feature name is in `_VALID_THEORY_CONSTRUCTS` (the 7 paper constructs) |
| 1 | `TARGET_IN_FEATURES` | CRITICAL | Yes | Feature name exactly equals `target_col` |
| 2 | `LEGACY_DISABLED` | CRITICAL | Yes | Feature name is in `LEGACY_DISABLED_CONSTRUCTS` AND NOT in `_VALID_THEORY_CONSTRUCTS` |
| 3 | `PROXY_LEAKAGE` | CRITICAL | Yes | Feature name (lowercased) contains any keyword from `PROXY_LEAKAGE_KEYWORDS` in `config/settings.py` |
| 4 | `TARGET_ADJACENT` | CRITICAL | Yes | Feature name (lowercased) contains any keyword from `_TARGET_ADJACENT_KEYWORDS` in `model_input_contract.py` |
| 5 | `ID_MEMORIZATION` | HIGH | Yes | Feature name (lowercased) contains any keyword from `_ID_COLUMN_KEYWORDS` in `model_input_contract.py` |
| 6 | `PREPROCESSING_LEAKAGE` | MEDIUM | No — warns only | Feature name (lowercased) contains any keyword from `_PREPROCESSING_KEYWORDS` in `model_input_contract.py` |
| 7 | `CONSTRUCT_LEAKAGE_FLAGGED` | CRITICAL | Yes | `column_mappings` is provided, feature name is a key in it, and `column_mappings[feat].leakage_flag == True` |

**Note on Check 6 (`PREPROCESSING_LEAKAGE`):** This is the only check that does not issue a `continue` after triggering. A feature with a preprocessing-leakage keyword name may still pass checks 7 (leakage flag) if those conditions are not met. The MEDIUM severity means it is logged and recorded in the violations list but does not contribute to `n_critical` or `n_high`, and therefore does not by itself invalidate the feature set.

## 4. Check-by-Check Design Rationale

### 4.1 Check 0 — Theory Construct Pre-Approval

**Trigger:** Feature name in `_VALID_THEORY_CONSTRUCTS`

**Approved set:**
```python
_VALID_THEORY_CONSTRUCTS: Set[str] = {
    "SatisfactionIndex", "BurnoutRisk", "EngagementScore",
    "TenureRatio", "IncomePerLevel", "CareerProgression", "SalaryGrowth",
}
```

These are the 7 constructs computed by `TheoryGroundedConstructEngine` from exact paper formulas. They are placed first in the check order because several of them share names — or partial lexical tokens — with patterns that later checks would flag:

- `"SatisfactionIndex"` contains `"index"` — which appears in `_ID_COLUMN_KEYWORDS`
- `"BurnoutRisk"` is in `LEGACY_DISABLED_CONSTRUCTS` — which Check 2 would block
- `"EngagementScore"` is also in `LEGACY_DISABLED_CONSTRUCTS`
- `"SatisfactionIndex"` is also in `LEGACY_DISABLED_CONSTRUCTS`

Without Check 0, the theory-engine versions of these constructs would be incorrectly blocked by Check 2 or 5. Section 5 of this document covers this naming collision in detail.

**Why pre-approval rather than exemption within each check:** Pre-approval with an explicit `continue` is cleaner than inserting `AND feat not in _VALID_THEORY_CONSTRUCTS` into every downstream check. It also makes the intent explicit and auditable in a single location.

---

### 4.2 Check 1 — TARGET_IN_FEATURES

**Trigger:** `feat == target_col`

The most direct form of leakage: the attrition label itself appears in the feature list. This should be caught by upstream pipeline code, but the contract provides a final safety net.

**Severity: CRITICAL** — there is no scenario in which including the target column as a feature is acceptable. AUC scores with this pattern will be ~1.0 (the model trivially predicts from the label it was asked to predict).

**Action: Block + continue.** No further checks for this feature.

---

### 4.3 Check 2 — LEGACY_DISABLED

**Trigger:** Feature name in `LEGACY_DISABLED_CONSTRUCTS` AND not in `_VALID_THEORY_CONSTRUCTS`

The 15 Layer B/C constructs in `LEGACY_DISABLED_CONSTRUCTS` were computed using wrong formulas, invented composites, or invalid construction methods (see `LEGACY_LOGICAL_QUARANTINE_REPORT.md`). If one of these columns reaches the model input contract, it means either:

- The `FeatureFactory` gate failed (Layer B ran when it should not have), or
- A cached or pre-computed DataFrame from a pre-Phase 4 run was used, or
- A developer manually inserted the column

All three scenarios are CRITICAL governance failures. The contract enforces a second line of defense against this.

**The exemption for `_VALID_THEORY_CONSTRUCTS`** is necessary because `SatisfactionIndex`, `BurnoutRisk`, and `EngagementScore` appear in both lists. See Section 5.

**Severity: CRITICAL** — using a construct with an invalid formula produces scientifically meaningless feature importances and model coefficients.

**Action: Block + continue.**

---

### 4.4 Check 3 — PROXY_LEAKAGE

**Trigger:** Feature name (lowercased) contains any keyword from `PROXY_LEAKAGE_KEYWORDS`

```python
PROXY_LEAKAGE_KEYWORDS: List[str] = [
    "attrition", "exit", "resigned", "resignation", "turnover", "left",
    "terminated", "termination", "churn", "quit", "separated", "separation",
    "leave", "voluntary", "involuntary", "last_day", "final_day",
    "reason_for", "job_opportunities", "no_longer", "departure",
    "status_change", "end_date", "offboard",
]
```

These keywords appear in column names that encode the attrition outcome directly (e.g., `attrition_flag`, `voluntary_leave`, `exit_status`). Such columns are frequently present in HR datasets where the attrition event is tracked alongside predictive features in the same table.

This check is defined in `config/settings.py` (not hard-coded in `model_input_contract.py`) so that the same keyword list is shared with other leakage detection components (`LeakageDetector`, `TemporalValidationGuard`).

**Severity: CRITICAL** — any column containing these keywords in its name is almost certainly encoding post-outcome information.

**Action: Block + continue.**

---

### 4.5 Check 4 — TARGET_ADJACENT

**Trigger:** Feature name (lowercased) contains any keyword from `_TARGET_ADJACENT_KEYWORDS`

```python
_TARGET_ADJACENT_KEYWORDS: List[str] = [
    "attrition_risk", "retention_risk", "churn_score", "resignation_score",
    "flight_risk", "turnover_risk", "stability_score", "stay_probability",
    "predicted_tenure", "exit_risk", "offboard", "final_status",
    "exit_reason", "separation_reason", "last_day", "last_working_day",
    "offboarding_date", "end_date", "termination_date",
]
```

Target-adjacent columns are derived risk scores or post-outcome dates — not raw outcome labels, but columns that encode information that is only knowable after the attrition event has occurred. Examples:

- `flight_risk_score` — a prior model's prediction, which if used as a feature creates a self-referential feedback loop
- `last_working_day` — a date that is only recorded for employees who left; including it reveals exactly who the model should label as "attrition = 1"
- `predicted_tenure` — a derived estimate that may have been computed using the outcome variable

**Distinction from Check 3 (PROXY_LEAKAGE):** Check 3 targets raw column names that directly encode the event. Check 4 targets derived risk scores and administrative post-outcome columns. Some keywords appear in both lists (e.g., `exit_risk`); the `continue` after Check 3 means a column matching both would be caught by Check 3 and never reach Check 4.

**Severity: CRITICAL** — derived risk scores as features cause circular predictions; post-outcome dates cause complete information leakage.

**Action: Block + continue.**

---

### 4.6 Check 5 — ID_MEMORIZATION

**Trigger:** Feature name (lowercased) contains any keyword from `_ID_COLUMN_KEYWORDS`

```python
_ID_COLUMN_KEYWORDS: List[str] = [
    "employee_id", "employeeid", "emp_id", "empid",
    "rownum", "row_num", "rowid", "row_id",
    "index", "idx", "serial", "seq", "uuid", "guid",
    "badge_number", "badge_no", "badgenumber",
]
```

Row-level identifiers allow a model to memorize individual records. In a tree-based model, a unique employee ID will have maximum information gain on the first split and produce an overfit model with near-perfect training accuracy and poor generalization.

**Why HIGH, not CRITICAL:** This is the most significant design decision in the severity classification. There are scenarios where including an identifier-like column is not harmful:

- A column named `"sequential_dept_index"` that happens to contain `"index"` but is not an employee-unique identifier
- A hashed or anonymized ID that has been deliberately included to test for memorization (as a diagnostic, not a training feature)
- A group-level ID (department code, site ID) that is ordinal and analytically meaningful

The `_ID_COLUMN_KEYWORDS` list uses substring matching on lowercased names, which means `"index"` would match both `"employee_index"` (true ID) and `"engagement_index"` (not an ID). The HIGH severity means the contract flags the column and blocks it — the caller must confirm it is genuinely an identifier before proceeding. CRITICAL would be appropriate only if every match were guaranteed to be harmful, which is not true with name-based heuristics.

**Note on `_VALID_THEORY_CONSTRUCTS` intersection:** `"SatisfactionIndex"` contains `"index"`, which is in `_ID_COLUMN_KEYWORDS`. Without Check 0, the theory-grounded `SatisfactionIndex` would be blocked here with HIGH severity. Check 0 prevents this.

**Severity: HIGH** — blocks the feature set (`is_valid = False` when `n_high > 0`) but is classified as a likely rather than certain violation.

**Action: Block + continue.**

---

### 4.7 Check 6 — PREPROCESSING_LEAKAGE

**Trigger:** Feature name (lowercased) contains any keyword from `_PREPROCESSING_KEYWORDS`

```python
_PREPROCESSING_KEYWORDS: List[str] = [
    "scaled", "imputed", "encoded", "normalised", "normalized", "_norm",
]
```

Columns with these suffixes or substrings suggest that a preprocessing transformation was applied to the entire dataset before the train/test split. If `StandardScaler` is fit on all rows including the test set before splitting, the test set statistics leak into the training process, inflating CV metrics.

**Why MEDIUM (warn, do not block):** The contract cannot determine from a column name alone whether the transformation was applied before or inside CV folds. A column named `"salary_scaled"` might have been scaled inside each fold of a scikit-learn Pipeline (safe) or scaled globally before any splitting (leakage). The name provides a useful signal, but blocking on this signal alone would produce too many false positives and would penalize teams that use correct fold-safe preprocessing.

The MEDIUM warning instructs the engineer to verify the transformation provenance and rename the column if it is confirmed to be fold-safe (which removes the warning on future runs).

**Severity: MEDIUM** — warns and records the violation but does not contribute to `n_critical` or `n_high`. Does not by itself cause `is_valid = False`.

**Action: Record violation, do NOT issue `continue`.** Evaluation continues to Check 7 for this feature.

---

### 4.8 Check 7 — CONSTRUCT_LEAKAGE_FLAGGED

**Trigger:** `column_mappings` provided AND `feat in column_mappings` AND `column_mappings[feat].leakage_flag == True`

This check is only active when the caller passes the Phase 1 `column_mappings` dict (from `TheoryAwareColumnMapper`). The mapper assigns `leakage_flag = True` to columns it identifies as outcome-proxies or temporally problematic during the semantic mapping phase.

This check provides a second, evidence-based leakage signal that is complementary to the keyword-based checks. The Phase 1 mapper has richer context — it considers column statistics, unique ratio, and semantic content — and its `leakage_flag` decisions are more reliable than pure name matching.

**Why CRITICAL when Phase 1 flagged it:** If Phase 1 governance already determined a column is a leakage risk, overriding that decision without documented justification would undermine the entire governance chain. The contract treats Phase 1 flags as authoritative.

**Severity: CRITICAL** — the column was examined by Phase 1 governance and found to be a leakage risk. This is not a heuristic match; it is an explicit governance judgment.

**Action: Block + continue.**

## 5. Theory Construct Pre-Approval: The Naming Collision Problem

### 5.1 The Collision

Three of the 7 theory-grounded constructs share their names with constructs in `LEGACY_DISABLED_CONSTRUCTS`:

| Construct Name | In `_VALID_THEORY_CONSTRUCTS` | In `LEGACY_DISABLED_CONSTRUCTS` | Collision Risk |
|---|---|---|---|
| `SatisfactionIndex` | Yes | Yes | Check 2 would block without Check 0 |
| `BurnoutRisk` | Yes | Yes (as `BurnoutRiskComposite`) | No collision — different names |
| `EngagementScore` | Yes | Yes | Check 2 would block without Check 0 |

Additionally, several theory construct names contain substrings that match other check keywords:

| Construct Name | Keyword Match | Check That Would Trigger | Effect Without Check 0 |
|---|---|---|---|
| `SatisfactionIndex` | `"index"` | Check 5 (`ID_MEMORIZATION`) | Blocked with HIGH severity |
| `CareerProgression` | None problematic | — | No collision |
| `TenureRatio` | None problematic | — | No collision |
| `IncomePerLevel` | None problematic | — | No collision |

### 5.2 Why the Theory-Engine Versions Are Correct

`SatisfactionIndex` in the theory engine is computed as:

```
(JobSatisfaction + EnvironmentSatisfaction + RelationshipSatisfaction + WorkLifeBalance) / 4
```

This is a four-input arithmetic mean with no prior normalization, anchored in Conservation of Resources (COR) theory and the "caravan of resources" principle.

`SatisfactionIndex` in Layer B (`feature_factory.py`) was computed as:

```
_norm(satisfaction) × 0.55 + _norm(engagement) × 0.45
```

This is a two-input weighted average that normalizes before combining — changing the scale and losing two required theoretical dimensions.

They are the same name but fundamentally different mathematical objects. The contract's Check 0 correctly identifies the theory-engine version by name and exempts it, while Check 2 would correctly block any legacy Layer B version that somehow entered the feature set.

### 5.3 How the Disambiguation Works

The disambiguation relies on the assumption that `TheoryGroundedConstructEngine` is the only code that produces columns named `SatisfactionIndex`, `EngagementScore`, etc. in theory-grounded mode. This is enforced by:

1. `FeatureFactory.engineer()` in theory-grounded mode does not produce these names (Layer B is gated off)
2. The cleanup sweep in `engineer()` removes any pre-existing legacy column with these names from the DataFrame
3. `TheoryGroundedConstructEngine` produces them only when evidence quality thresholds are met

If both a legacy and a theory-engine version were somehow present simultaneously, the cleanup sweep would remove the legacy version, leaving only the theory-engine version for the contract to validate.

## 6. Severity Classification Rationale

The contract uses three severity levels. The mapping is:

| Severity | `is_valid` Impact | Block Feature? | Design Rationale |
|---|---|---|---|
| CRITICAL | Yes — any CRITICAL → `is_valid = False` | Yes | Certain violation: the harm is definitive and the false positive rate of the check is low |
| HIGH | Yes — any HIGH → `is_valid = False` | Yes | Probable violation: the harm is severe but edge cases exist where the check could be wrong |
| MEDIUM | No — MEDIUM alone does not invalidate | No | Possible violation: the check produces too many false positives to block automatically |

### 6.1 Why ID Memorization Is HIGH, Not CRITICAL

Identifier columns are not always harmful — they are harmful specifically when they are unique per row and the model is trained on tabular data without regularization. A column named with `"index"` in its name might be:

- A department-level index (e.g., 10 departments → 10 distinct values) — not harmful, high information value
- An employee-unique integer ID — harmful, enables memorization
- A composite key like a hashed `"org_index"` used for grouping — ambiguous

The check cannot distinguish these cases from the column name alone. Blocking with CRITICAL severity would reject legitimate columns too often. HIGH severity forces manual review — which is the correct outcome when the check is uncertain.

### 6.2 Why Preprocessing Leakage Is MEDIUM

Preprocessing leakage depends entirely on where in the pipeline the transformation was applied. A column named `"age_scaled"`:

- **Safe:** Scaled inside each fold of a scikit-learn Pipeline → no leakage
- **Unsafe:** Scaled globally before `train_test_split()` → test statistics in training

The column name is the same in both cases. The contract cannot determine provenance from the name. MEDIUM severity generates a warning that prompts the engineer to verify, without blocking pipelines that use correct fold-safe preprocessing.

## 7. Validity Decision Logic

```python
n_critical = sum(1 for v in violations if v.severity == "CRITICAL")
n_high     = sum(1 for v in violations if v.severity == "HIGH")
n_medium   = sum(1 for v in violations if v.severity == "MEDIUM")

is_valid = (n_critical == 0 and n_high == 0)
```

The `approved_features` list contains all feature names that were not added to `blocked`. MEDIUM violations do not block features; features with only a MEDIUM flag remain in `approved_features`.

**Implication:** A feature set can have MEDIUM violations and still be `is_valid = True`. The caller is responsible for reviewing and addressing MEDIUM warnings before production use. This is documented in the `ContractValidationResult.governance_notes` field.

## 8. Output: ContractValidationResult Dataclass

```python
@dataclass
class ContractValidationResult:
    is_valid: bool
    approved_features: List[str]
    blocked_features: List[str]
    violations: List[ContractViolation]
    n_critical: int
    n_high: int
    n_medium: int
    scientific_feature_mode: str
    summary: str
    governance_notes: List[str] = field(default_factory=list)
```

| Field | Type | Description |
|---|---|---|
| `is_valid` | `bool` | `True` if and only if `n_critical == 0 AND n_high == 0`. Gate condition for model training. |
| `approved_features` | `List[str]` | Feature names that passed all checks (or were pre-approved at Check 0). MEDIUM-violation features are included here. |
| `blocked_features` | `List[str]` | Feature names that triggered a CRITICAL or HIGH violation and must not enter the model. |
| `violations` | `List[ContractViolation]` | Full list of violations found, one per feature-check pair. Each violation has: `feature_name`, `violation_type`, `severity`, `reason`, `recommendation`. |
| `n_critical` | `int` | Count of CRITICAL violations found across all features. |
| `n_high` | `int` | Count of HIGH violations found across all features. |
| `n_medium` | `int` | Count of MEDIUM violations found across all features. |
| `scientific_feature_mode` | `str` | Value of `SCIENTIFIC_FEATURE_MODE` at validation time. Recorded for audit trail purposes. |
| `summary` | `str` | Single-line human-readable summary. Format: `"Contract [VALID|INVALID]. N features blocked (X CRITICAL, Y HIGH, Z MEDIUM violations). M features approved."` |
| `governance_notes` | `List[str]` | Additional notes, e.g., list of theory-grounded constructs that passed, or reminders about the active mode. |

### 8.1 ContractViolation Dataclass

```python
@dataclass
class ContractViolation:
    feature_name: str
    violation_type: str    # One of the 7 violation type strings
    severity: str          # "CRITICAL" / "HIGH" / "MEDIUM"
    reason: str            # Full human-readable explanation
    recommendation: str    # Specific remediation action
```

## 9. Governance Integration: Pipeline Placement

### 9.1 Call Site

The contract is called in the ML pipeline after feature engineering and before model training. The canonical call pattern is:

```python
from backend.core.model_input_contract import ModelInputContract

contract = ModelInputContract()
result = contract.validate(
    feature_names=feature_list,
    df=df,
    target_col=target_col,
    column_mappings=theory_mappings,   # from TheoryAwareColumnMapper
)

if not result.is_valid:
    raise ValueError(result.summary)
```

The `validate_model_inputs()` convenience function provides a one-call wrapper that internally instantiates `ModelInputContract` and calls `validate()`:

```python
from backend.core.model_input_contract import validate_model_inputs

result = validate_model_inputs(feature_names, df, target_col, column_mappings)
```

### 9.2 Relationship to Upstream Components

| Upstream Component | Data Passed to Contract |
|---|---|
| `TheoryAwareColumnMapper.map(df)` | `column_mappings` — carries `leakage_flag`, `evidence_strength` for Check 7 |
| `TheoryGroundedConstructEngine.compute(df, mappings)` | Adds theory construct columns to `constructed_df`; their names appear in `feature_names` |
| `FeatureFactory.engineer(df, sem_map, ...)` | Adds Layer A, D, E features to DataFrame; their names appear in `feature_names` |

The contract does not call any of these components itself. It receives the assembled feature name list and validates it.

### 9.3 Relationship to Downstream Components

| Downstream Component | Contract's Role |
|---|---|
| `MLRouter` | Contract must return `is_valid = True` before `MLRouter` begins training |
| `AutoMLEngine` | Same requirement — AutoML hyperparameter search should not run on an invalid feature set |
| `ReportGenerator` | Feature names used in report SHAP plots must match the approved feature set |
| `GovernanceLogger` | `ContractValidationResult` should be logged by the governance logger for audit trail |

### 9.4 What the Contract Does Not Guard Against

The contract is scoped to **name-based feature list validation**. It does not:

- Check column value distributions or statistics
- Detect numeric leakage (e.g., a continuous score that is highly correlated with the target but has an innocuous name)
- Verify the mathematical correctness of a theory construct's values
- Enforce train/test split correctness (this is delegated to `TemporalValidationGuard`)
- Check model hyperparameters or training procedures

These gaps are known and documented in Section 11.

## 11. Known Limitations

The contract is a name-based heuristic tool. The following limitations are acknowledged and documented.

### 11.1 False Positives (Clean Features Incorrectly Flagged)

| Scenario | Check | Example |
|---|---|---|
| Column name contains a leakage keyword but is not a leakage column | Check 3 | `"leave_days_unused"` — about unused vacation, not attrition |
| Column name contains an ID keyword but is not row-unique | Check 5 | `"department_index"` — 10 departments, not employee-unique |
| Column name contains a preprocessing keyword but was fold-safe | Check 6 | `"experience_normalized"` — normalized inside CV correctly |
| Column name contains target-adjacent keyword but predates the outcome | Check 4 | `"predicted_tenure_at_hire"` — computed at hire, not post-event |

**Mitigation:** Engineering teams should rename columns to avoid ambiguous names. The contract's `recommendation` field in each `ContractViolation` specifies what action to take. MEDIUM violations specifically ask for verification before blocking.

### 11.2 False Negatives (Harmful Features That Pass the Contract)

| Scenario | Check Missed | Example |
|---|---|---|
| A leakage column whose name contains no trigger keywords | All checks | `"hr_process_flag"` — encodes whether an exit process was initiated |
| A theory-adjacent formula error that produces valid-looking values | No check exists | A manually constructed feature that approximates the attrition label but is named `"workload_composite"` |
| A target leak encoded in a numeric value distribution | No check exists | A salary column that has been manually set to a sentinel value for employees who left |
| A column with future data (post-prediction-date) | No check exists | `"next_review_date"` — if the dataset includes reviews scheduled after the prediction window |

**Mitigation:** These scenarios require human data review, content-based leakage detection (`LeakageDetector`), and temporal validation (`TemporalValidationGuard`). The contract is one of several governance components, not a complete substitute for expert review.

### 11.3 Name-Based Heuristics Cannot Detect Value-Level Leakage

The contract does not have access to column statistics. It cannot detect:

- A column where the distribution in the training set differs from the test set (indicative of preprocessing leakage)
- A column with bimodal distribution that exactly separates the two attrition classes
- A column with a suspiciously high Pearson or mutual information correlation with the target

These analyses are the responsibility of `ModelTruthAudit`, `LeakageDetector`, and the feature trustworthiness engine.

### 11.4 Substring Matching Is Sensitive to Column Naming Conventions

The contract uses simple substring containment (`keyword in feat.lower()`). This means:

- `"attrition"` in the keyword list matches `"pre_attrition_survey"` (correct block) but also `"nonattrition_status"` (potentially a false positive if the column is genuinely pre-outcome)
- `"index"` in the ID keyword list matches any column name containing `"index"` regardless of context

Teams using column naming conventions that include these terms for legitimate purposes should consult with the science lead to determine whether a column-level override mechanism is needed in a future version of the contract.

## 12. Operational Guidance for Engineering Teams

### 12.1 When the Contract Returns `is_valid = False`

1. Read `result.summary` for a high-level count of violations.
2. Iterate `result.violations` to see each blocked feature, its violation type, and the recommended action.
3. Remove blocked features from the feature list (or resolve the underlying issue if the block is a false positive).
4. Re-run the contract on the revised feature list.
5. Do not bypass `is_valid = False` by catching and suppressing the exception — this would constitute a governance violation.

### 12.2 When the Contract Returns MEDIUM Violations with `is_valid = True`

1. Review each MEDIUM violation individually.
2. For `PREPROCESSING_LEAKAGE` warnings: verify that the flagged transformation was applied inside CV folds. If confirmed safe, rename the column to remove the triggering keyword.
3. Do not proceed to production deployment with unresolved MEDIUM warnings without documented justification.

### 12.3 Convenience Function

For standard pipeline use where `column_mappings` is available from Phase 1:

```python
from backend.core.model_input_contract import validate_model_inputs

result = validate_model_inputs(
    feature_names=feature_list,
    df=df_enriched,
    target_col="Attrition",
    column_mappings=phase1_mappings,
)
```

For lightweight checks where Phase 1 mappings are not available (e.g., quick unit tests):

```python
result = validate_model_inputs(
    feature_names=feature_list,
    target_col="Attrition",
)
# Note: Check 7 (CONSTRUCT_LEAKAGE_FLAGGED) is skipped when column_mappings is None
```

### 12.4 Adding New Keywords to the Contract

If new proxy leakage keywords are identified (e.g., from a dataset where attrition is encoded as `"workforce_exit"`):

- Add to `PROXY_LEAKAGE_KEYWORDS` in `config/settings.py` (shared with other leakage detection components)
- Do NOT add to `_PREPROCESSING_KEYWORDS`, `_TARGET_ADJACENT_KEYWORDS`, or `_ID_COLUMN_KEYWORDS` inside `model_input_contract.py` unless the keyword is specific to that check category
- Run the full test suite after adding keywords to verify no new false positives are introduced for the 7 theory constructs or common clean feature names
